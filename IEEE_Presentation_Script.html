IEEE Query Quest 2026
Presentation Script & Q&A Guide

1. The Introduction (Hooking the Judges)

"Good morning respected judges. Welcome to our presentation. Today, we are not just presenting a Hospital Management System. We are presenting a highly secure, zero-trust healthcare platform protected by our custom 'SentinDB Security Layer'. Healthcare data is incredibly sensitive, yet basic SQL Injection and Privilege Creep remain the leading causes of data breaches in modern fintech and medical apps. Our project solves this."

2. Explaining What You Did (The Theory)

Explain the core problem: Most applications take user input and trust it blindly. If a user types malicious SQL code into an email field, the database might execute it, leaking patient data.

Explain your solution (SentinDB):

  • We built an AST Query Tokenizer: It intercepts the query before it hits the database and uses parameterized binding. This means input is treated strictly as text, not executable code.
  • We built a Dynamic ABAC Matrix (Attribute-Based Access Control): It stops Privilege Creep by evaluating a 3-tuple (Subject, Resource, Action) before allowing access to sensitive routes like doctor earnings or audit logs.

3. The Practical Demonstration (The Security Lab)

"Sir, to clearly demonstrate how our defense works, we built an interactive Security Lab directly into our app. Let me show you a live simulation."

Step-by-step actions on stage:

  1. Open the Security Lab page.
  2. Show SQL Injection: Click the "Tautology Bypass" preset (' OR '1'='1).
    • Point to the red "Without Layer" side: "As you can see, a standard unprotected query blindly concatenates the string. The database evaluates 1=1 as TRUE and leaks the entire user table."
    • Point to the green "With SentinDB" side: "But with our SentinDB layer, the AST Tokenizer intercepts the payload, parameterizes it as `%s`, and neutralizes the threat completely. Zero rows are leaked."
  3. Show Privilege Creep: Switch to the "Privilege Creep" tab. Select "Patient to Doctor Earnings".
    • Point to the red side: "Without dynamic ABAC, a logged-in patient might manipulate the URL to access doctor salaries."
    • Point to the green side: "Our ABAC matrix evaluates the patient's context and blocks the lateral escalation at the gateway level."

4. Expected Judge Questions & How to Answer Them

Judge: "How does your SentinDB layer actually stop the SQL Injection?"
Answer: "Sir, we use Parameterized Queries combined with an AST (Abstract Syntax Tree) tokenizer. Instead of concatenating strings directly into the SQL command, our layer sends the SQL structure and the user data separately to the database driver. The database treats the malicious input strictly as a literal string value, completely stripping its ability to execute as code."
Judge: "Why did you build an ABAC matrix instead of standard RBAC (Role-Based Access Control)?"
Answer: "RBAC is static and prone to Privilege Creep. ABAC (Attribute-Based Access Control) evaluates the dynamic context—the Subject (who is asking), the Resource (what they want), and the Action (what they want to do). This completely neutralizes lateral escalation because access is evaluated per-request based on strict boundaries."
Judge: "Is this simulation running against real tables?"
Answer: "Yes, sir. It targets our actual `users_user` table in Supabase PostgreSQL. The 'Without Layer' simulation intentionally uses an insecure raw `cursor.execute()` string concatenation to prove the vulnerability exists, while the 'With Layer' uses our secure parameterized pipeline on the exact same database."

5. Closing the Presentation

"In conclusion, our Hospital Management System doesn't just manage appointments; it strictly defends patient privacy at the database layer. By neutralizing SQL injection and Privilege Creep, we've built a robust, zero-trust architecture. Thank you."
