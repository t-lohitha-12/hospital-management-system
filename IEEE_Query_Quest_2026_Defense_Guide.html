SentinDB Security Lab

This guide explains the key vulnerabilities demonstrated in the SentinDB interactive lab, contrasting standard unprotected architectures with SentinDB's zero-trust gateway.

1. SQL Injection (SQLi)

SQL Injection occurs when untrusted user input is directly concatenated into a database query string. This allows attackers to manipulate the query's structure (Abstract Syntax Tree) to execute unauthorized commands.

Technical Definition

An attack targeting data-driven applications where malicious SQL statements are inserted into entry fields for execution (e.g. dumping database contents to the attacker).

Example: Tautology Bypass

Baseline Without Layer

Payload: ' OR '1'='1

Resulting Query:
SELECT * FROM users WHERE email = '' OR '1'='1'

Impact: Bypasses authentication because 1=1 is always true, returning all users.

Protected With SentinDB

Mechanism: AST Query Tokenizer

Resulting Query:
SELECT * FROM users WHERE email = %s

Impact: The input is treated strictly as a string literal, not executable code. Exploit isolated.

2. Privilege Creep

Privilege creep happens when users gradually accumulate access rights beyond what they strictly need for their current roles, or when systems fail to enforce context-aware access controls (ABAC) dynamically.

Technical Definition

The gradual accumulation of access rights over time, or the exploitation of static Role-Based Access Control (RBAC) where a lower-privileged role laterally accesses resources meant for another role.

Example: Lateral Escalation

Baseline Static RBAC

Scenario: A patient navigates to the doctor_earnings endpoint.

Impact: If the route lacks strict role verification, the patient views sensitive salary data.

Protected Dynamic ABAC

Scenario: SentinDB evaluates the 3-tuple: (Subject: Patient, Resource: doctor_earnings, Action: READ).

Impact: Clearance mismatch. Request is dropped at the gateway (403 Forbidden).
