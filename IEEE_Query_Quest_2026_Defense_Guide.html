1. Deep Dive: The 3 Core Database Vulnerabilities

Pillar 1: SQL Injection (SQLi)

Definition: An attack technique where untrusted user input is concatenated directly into a database query string, causing the Database Management System (DBMS) to mistake user-supplied data for executable SQL code.

General Analogy: Imagine a bank teller asking for your name. Instead of saying "Alice", you say "Alice, and also transfer $1,000,000 to my overseas account". If the teller executes everything verbatim without checking, your input hijacked the instruction.

Technical Mechanism: The SQL query parser compiles the string into an Abstract Syntax Tree (AST). By injecting quotation marks and boolean operators (e.g. ' OR 1=1 --), the attacker mutates the AST grammar tree, converting a conditional filter into a tautology that returns all records.

Pillar 2: Privilege Creep (Lateral & Vertical Escalation)

Definition: The gradual accumulation of access rights beyond what a user requires to perform their legitimate duties, or the exploitation of static Role-Based Access Control (RBAC) to read restricted tables (e.g., patient role reading doctor salaries or admin audit logs).

General Analogy: A hospital janitor whose keycard has accumulated master keys over the years, allowing them to walk into the CEO's office or pharmacy narcotics vault without any alarms.

Technical Mechanism: Static RBAC checks permissions at the route level rather than the query/column level. SentinDB introduces Dynamic Attribute-Based Access Control (ABAC), evaluating a 3-tuple (Subject, Resource, Action) in real-time.

Pillar 3: Unauthenticated Direct Database Access

Definition: Bypassing the application's authentication middleware (e.g., direct PostgreSQL port access, leaked connection poolers, or broken object-level authentication) allowing anonymous clients to execute queries.

Technical Mechanism: SentinDB enforces an Ephemeral Cryptographic Session Gatekeeper. Every query must carry a valid HMAC/JWT signature verified at the middleware edge before any DBMS connection socket is allocated.

2. Technical Architecture: Without Our Layer vs. With SentinDB

🔴 WITHOUT OUR LAYER (Vulnerable)

Raw string formatting directly concatenates untrusted input into SQL string:

Defense: The DBMS compiles the query structure first. The payload is treated purely as a literal string value, rendering injection syntax harmless.

5. Judges' Q&A Cheat Sheet (Anticipated Questions & Winning Answers)

Q1: "Why build an interceptor layer instead of just using prepared statements everywhere in code?"
Answer: "While prepared statements are the ideal standard, in enterprise architectures with legacy microservices, third-party reporting tools, and dynamic ORM queries, human error frequently leads to unparameterized queries. SentinDB acts as a Defense-in-Depth Layer that guarantees parameterization at the gateway, catching errors regardless of developer mistakes."
Q2: "What is the difference between RBAC and your ABAC Privilege Creep defense?"
Answer: "Role-Based Access Control (RBAC) grants static permissions based only on user title (e.g. 'Doctor'). Over time, permissions accumulate and create 'Privilege Creep'. SentinDB uses Attribute-Based Access Control (ABAC) which checks dynamic contextual attributes in real-time: user role, resource classification level, patient-doctor relationship, and session validity."
Q3: "Does SentinDB introduce performance latency to database operations?"
Answer: "Our benchmarks show an average processing overhead of only 0.8 to 1.2 milliseconds per query. Because regex tokenization and cryptographic signature checks occur in memory before network I/O, the performance overhead is negligible."
